# Issue 62: Supabase Management API free-plan evidence

Research scope: official Supabase documentation and official `supabase/supabase` documentation source only. No credentials or API mutations were used.

## Findings

- **Read an organization's plan:** `GET https://api.supabase.com/v1/organizations/{slug}`. The response schema includes `plan` (example: `"free"`). The endpoint requires `organizations:read`; fine-grained PAT permission is `organization_admin_read`. This is the reliable plan check. [API reference](https://supabase.com/docs/reference/api/v1-get-an-organization)
- **Read entitlements:** `GET /v1/organizations/{slug}/entitlements` returns entitlements derived from the plan and overrides. It is not a free-project-quota counter. [API reference](https://supabase.com/docs/reference/api/v1-get-organization-entitlements)
- **Free-project limit:** Supabase currently documents two active free projects per user, counted across all organizations where the user is Owner or Administrator; paused projects do not count. Org members who are Owners/Admins also affect whether a project can be launched. The official docs do not describe a Management API endpoint returning remaining free-project quota, so this needs account-wide assessment and can still be rejected by server-side quota enforcement. [Billing FAQ](https://supabase.com/docs/guides/platform/billing-faq) · [Billing overview](https://supabase.com/docs/guides/platform/billing-on-supabase)
- **`POST /v1/projects` `plan: "free"`:** the current API reference marks `plan` as **optional and deprecated**; current OpenAPI schema identifies it as ignored. Current official project-creation guidance omits `plan`. Do not treat it as a safety control or proof the created project is free. [Create a project](https://supabase.com/docs/reference/api/v1-create-a-project) · [OpenAPI reference](https://api.supabase.com/api/v1/) · [Supabase for Platforms](https://supabase.com/docs/guides/integrations/supabase-for-platforms)
- **Create organization:** `POST /v1/organizations` accepts only required `name` in its documented body (no plan selector), returning id/slug/name. The billing FAQ says organizations have one plan; billing docs and the official knowledge base describe newly created organizations as Free by default. Thus org creation is the supported route to a new Free-plan org, but the API response itself does not expose/guarantee `plan`; verify it with `GET /v1/organizations/{slug}` before creating a project. [Create organization](https://supabase.com/docs/reference/api/v1-create-an-organization) · [Free-plan org instructions](https://supabase.com/kb/troubleshooting/keeping-free-projects-after-pro-upgrade-Kf9Xm2) · [Billing overview](https://supabase.com/docs/guides/platform/billing-on-supabase)
- **Delete organization:** no organization-delete operation appears in the current Management API reference's Organizations operations. Supabase says a Free subscription continues indefinitely unless the organization is deleted in organization settings. Project deletion is available by `DELETE /v1/projects/{ref}`, but is permanent/irreversible. So API-created orgs should not be considered cleanly compensatable through a documented Management API delete operation. [API reference index](https://api.supabase.com/api/v1/) · [Manage subscription](https://supabase.com/docs/guides/platform/manage-your-subscription) · [Delete project](https://supabase.com/docs/guides/platform/delete-project)

## Decision for safe project creation

There is **no API-level guarantee** that `POST /v1/projects` with `plan: "free"` yields a free project: the field is ignored. Use `GET /organizations/{slug}` to verify the target organization is Free before project creation, and omit deprecated `plan`. The account-wide active-project cap is enforced across Owner/Admin memberships, so creating a new organization does not expand the user's two-project allowance. A successful request alone is not proof of the project's billing status; verify the organization association and plan.
